## ARCHITECTURE DECISION — CLIENT-CENTRIC (the clean realization of the 6 deltas)
The review's deltas (time-local restraint → client, fire-on-surface → client, due-signal is
client-computable) LOGICALLY imply a client-centric PRO-1 — which also drops the server-scheduler's
layering violation + server-timezone + fire-on-post race. So: **the client ticks while the app runs;
the CORE pure evaluator is called client-side with the REAL LOCAL clock; trigger DEFINITIONS live in
the entity store; fire STATE in a raw-JSON route. NO server scheduler in PRO-1** — background/closed-app
push (Electron main / OS scheduler / mobile) is explicitly **PRO-3**. This is the text-first, app-running
target the design doc describes. Core primitives (trigger entity + pure evaluateTrigger) are unchanged
from the reviewed plan; only "who ticks" moved server→client, which the deltas already required.

## CORE-vs-PLUGIN (kernel law — trigger EARNS core; trim the unions)
- **CORE (small, new):** `trigger` entity (definitions) + pure `evaluateTrigger` (restraint). Domain-neutral "when X, fire actionRef, respecting restraint" = `operation` (behavior-as-data) extended to TIME; the design doc names ≥5 downstream consumers (Feynman/口语/睡前3问/streak/复习). The temporal analogue of operation → genuinely core.
- **BUILT-IN PLUGIN (the exemplar):** the review-push is a CODE-registered built-in trigger (like built-in operations/note-types are code, while user ones are entities) — NOT a seeded entity. PRO-1 registers ONE built-in; the entity store is set up for FUTURE user triggers (none seeded in PRO-1).
- **CLIENT host-chrome:** NudgeToast (clone DraftNoteToast) + `new Notification()`.

## THE 6 FOLDED DELTAS (MANDATORY)
1. **Timezone → CLIENT.** The pure `evaluateTrigger` takes an injected LOCAL clock context `{ nowMs, localHhmm, localDayKey }` computed CLIENT-side (the client owns `new Date()` local). Quiet-hours + local-day cap + day-rollover all evaluate against these. NO server-side local-time math (codebase is 100% UTC epoch — grep confirmed zero local-time machinery).
2. **Fire-on-SURFACE, not post.** `lastFiredAt`/`firedTodayCount` are recorded when the client SURFACES the nudge (the client POSTs the fire), NOT when a candidate is computed. Restraint governs what the user SEES.
3. **Due-signal = CLIENT-computed** (delta #3 layering violation EVAPORATES): the client tick reuses the EXISTING `GET /api/review/schedule` (app.ts:862) + notes + `reviewDueStats` (src/client/review/queue.ts:326 — stays client, NO promotion needed since the CLIENT computes it, exactly as ReviewPanel.tsx:337 already does).
4. **Trigger DEFINITIONS → entity store** — a new `triggers.jsonl` store line (entities.ts idiom, "one line + a schema"), `triggerSchema` via `recordEnvelopeSchema` (operation.ts:26 precedent), kept OUT of `vaultEntitySchema` (schema/index.ts:25-30, like operation). Fire/nudge STATE → raw JSON (`trigger-fires.json`, operation-prefs `vault.storage` idiom, workspace.ts:152).
5. **Trim PRO-1 to `when:"schedule"` + `actionRef:"navigate"` ONLY.** The schema's discriminated unions may DEFINE `event`/`operation` variants (forward-compat) but the PRO-1 evaluator REJECTS them (event needs a memory-event hook not built; operation.run needs focus — registry.ts:746-759 — so can't run headless). Keep the full 6-field restraint schema.
6. **Add:** pending-nudge TTL (drop pendings not from today) + dedupe by `triggerId+localDayKey`; `Notification.permission` gate → `requestPermission()` once → **fall back to the in-app NudgeToast when default/denied** (toast is the primary surface, notification is the enhancement); **new-user arming guard** — the review-push trigger arms only after some graded history (empty/absent `review-schedule.json` makes `reviewDueStats` count ALL eligible notes as due — queue.test.ts:661 — so a fresh importer would be nagged day-one; guard: require ≥1 note WITH a schedule record, or an account-age/graded-count floor); gate any test-only tick route behind an env flag.
