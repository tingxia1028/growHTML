Code Review Companion

Growte / growHTML 代码评审对照文档

这个项目的核心不是“页面怎么排版”，而是一个本地优先的学习资料系统： 用户打开资料，选中原文位置，创建锚点和笔记，再让 AI 围绕这些上下文解释、出题、复习。 评审时最重要的是守住对象边界、数据流、持久化兼容和前端注册式扩展点。

使用方式：先读第 1 节和第 2 节，再根据 PR 类型跳到第 11 节。 每个路径都是相对 growHTML/ 的路径，可以在编辑器里直接搜索。

1. 先从哪里看

不要从随机组件开始看。这个仓库层次多、注册点多，正确起步是先判断 PR 属于哪条主链路。

先看 4 个入口文件

  1. src/server/start.ts：服务如何启动、打开 vault、迁移、创建 API。
  2. src/server/app.ts：HTTP API 如何接到 service。
  3. src/client/App.tsx：前端组合根。
  4. src/client/workspace/WorkspaceShell.tsx：工作台布局如何渲染。

再按改动类型追链路

  • 改数据：schema -> store -> service -> route -> entityClient -> UI。
  • 改 UI：view registry -> WorkspaceContext domain hook -> entityClient。
  • 改 AI：command -> server AI service -> provider -> structured output。
  • 改 Electron：main/preload IPC -> renderer platform adapter。

一个标准 review 顺序

  1. 读 PR 描述，判断它是在加“对象、视图、命令、AI operation”，还是在改底层机制。
  2. 看测试先行不先行：有没有贴近改动范围的单测或 e2e。
  3. 从 schema/API 边界开始，看输入是否被 zod 校验，错误是否是 typed error。
  4. 追到持久化，看是否兼容旧数据、软删除、导入导出、SQLite/JSONL 回退。
  5. 追到前端，看是否通过 registry/context/command 接入，而不是组件互相硬连。
  6. 最后看 UI 文案、状态、空态、失败态、加载态、可访问性。
评审重点：这个仓库已经有很多“扩展点”。如果一个 PR 为了加新功能到处改核心文件， 优先怀疑它没有用已有注册机制。

2. 产品和数据模型

你只要先记住这条链路，很多代码就能对上：

Source 原始资料 -> Anchor 原文位置 -> Note 学习记录 -> Layer 可开关、可分享的学习层 -> Viewer 不同资料类型的显示和定位 -> AI 围绕 source/anchor/note 做解释、生成、复习
对象 含义 关键文件 review 关注点
Source 原始学习资料。可以是 HTML、PDF、图片、网页、代码等。 src/core/schema/source.ts
src/server/services/sources.ts		 不要复制出第二套“真相”；文件路径、hash、origin、revision 是否正确。
Anchor 资料里的一个位置：文本选区、PDF 页码和 rect、图片区域、网页 text quote。 src/core/schema/anchor.ts
src/server/services/anchors.ts		 定位信息是否足够恢复；quote/rect/page 是否按类型校验；是否避免孤儿 anchor。
Note 挂在 anchor/source/concept 上的学习记录。内容形状由 contentType 决定。 src/core/schema/note.ts
src/core/notes/contentTypes.ts
src/server/services/notes.ts		 content 是否按 spec 校验；新增 note 类型是否无需改核心 schema。
Layer 学习层，用来开关、组织、分享一组 note/anchor。 src/core/schema/study-layer.ts
src/core/study-layer/layers.ts		 可见性是否按 layerIds 计算；不要把某个 kit 的分类硬编码到 core。
Concept / Relation 概念和概念关系，用于图谱、双链、AI 自动标注。 src/core/schema/concept.ts
src/core/schema/relation.ts		 名称归一化、去重、merge、删除对关系图的影响。
MemoryEvent 学习行为事件，例如 review 结果，用于学习画像。 src/core/schema/memory.ts
src/server/memory.ts		 是否泄露隐私；managed AI 是否禁止默认带出 profileContext。

最重要的设计规则

  • 新增能力优先是一个 contentType、一个 view、一个 command、一个 AI operation，而不是新增核心对象。
  • note.content 是 unknown，必须由 NoteContentSpec 按 contentType 校验。
  • Anchor painting 是从 note/layer 可见性推导出来的，不应该只看 anchor 自己的 layer 字段。
  • AI 输出不要变成平行数据模型；它最终应该落到 Note、Patch、Concept、Relation、Layer 或 MemoryEvent。

3. 启动和运行时

Web/dev 模式

npm run dev -> concurrently -> npm run dev:server (tsx watch src/server/index.ts, API 默认 4177) -> npm run dev:client (vite, client 默认 5173) -> Vite 代理 /api 到 API server

生产 / Electron 模式

electron/main.ts -> resolveStartUrl() -> startServer({ clientDir: dist, vaultRoot: userData/vault }) -> BrowserWindow.loadURL(started.url) -> renderer 加载 React app -> renderer 通过 HTTP / IPC 访问本地能力
文件 作用 review 关注点
src/server/index.ts CLI/dev server 入口。 端口、clientDir、自动备份开关。
src/server/start.ts 打开 vault、迁移、创建 Express app、启动 HTTP server。 是否关闭 sqlite handle；测试是否注入临时 vault。
electron/main.ts 桌面主进程，创建窗口、IPC、启动本地 server。 renderer 是否无 Node 权限；openPath 是否只允许本地绝对路径。
electron/preload.ts 安全暴露少量 IPC 给 renderer。 不要把任意 Node API 暴露给前端。

4. 存储层

数据层的关键是 SnapshotStore。业务代码不直接写 SQLite 或 JSONL，只用统一接口。 

type SnapshotStore<T> = {
  list(): Promise<T[]>             // live records only
  listTrashed(): Promise<T[]>      // deletedAt records
  readWithIssues(): Promise<...>   // all records + parse issues
  get(id): Promise<T | null>       // live record
  getAny(id): Promise<T | null>    // live or trashed
  upsert(record): Promise<T>
  delete(id): Promise<boolean>     // real purge, not soft delete
}

默认引擎

当前代码里 STORE_ENGINE=jsonl 才回退 JSONL；未设置时默认 SQLite。 这点和少数旧注释不完全一致，review 时以 src/core/store/entities.ts 的 resolveDefaultEngine() 为准。

SQLite 怎么做

  • 每个实体一个表，基本 envelope 是 id / updatedAt / deletedAt / json。
  • 完整 record 保存在 json blob 里，所以 schema 改动不一定需要 SQL migration。
  • 常用字段会抽成索引列，例如 note 的 sourceId、contentType。
  • 多对多关系走 junction 表，例如 note_anchors、note_concepts、note_layers。
  • 搜索走 FTS 预过滤，再由服务层代码做 ranking。

软删除规则

软删除不是调用 store.delete。 软删除是给记录加 deletedAt 后 upsert； store.delete() 是真实清除，一般只给回收站 purge 用。

review 存储改动时问这些问题

  • 新增字段是否有默认值，旧数据能不能 parse？
  • 新增 entity 是否进了 entityFileNames、EntityStores、schema、服务层？
  • SQLite 和 JSONL 两条路径行为是否一致？
  • 导入/导出/备份是否需要 dump/load SQLite 到 JSONL？
  • 删除是软删除还是 purge？restore 怎么办？
  • 如果是搜索字段，FTS document 是否要更新？关联 anchor quote 改动是否会刷新 note FTS？

5. 后端服务层

服务层大体是：route 负责 HTTP 细节，service 负责业务逻辑，store 负责持久化。 评审时要防止业务逻辑直接堆在 route 里。

HTTP request -> src/server/app.ts route -> zod parse request body / query -> src/server/services/*.ts -> vault.stores.* -> response JSON

典型例子：创建笔记

  1. POST /api/notes 在 src/server/app.ts。
  2. body 用 createNoteRequestSchema 校验。
  3. 调用 src/server/services/notes.ts:createNote()。
  4. service 检查 contentType 是否注册。
  5. 用 parseNoteContent() 按 note 类型校验 content。
  6. 默认把 source note 放进 owned layer。
  7. 写入 vault.stores.notes.upsert(note)。

典型例子：创建 anchor

  1. POST /api/anchors 在 src/server/app.ts。
  2. 不同 anchorKind 要求不同字段：HTML 要 studyId 和 quote；PDF 要 page；图片要 rect。
  3. service 会 ensure source 存在，并给 anchor stamped owned layer。
  4. 孤儿 anchor 会在 note 删除或 listSourceAnchors 时被清理/软删除。

错误处理

优先使用 src/server/services/errors.ts 里的 typed errors，例如 NotFoundError、ValidationError、ForbiddenError。 这样 direct transport、HTTP route 和 UI 都能得到稳定的 status/code。

高风险点：src/server/app.ts 仍然很大，route 很多。 如果 PR 又往里面加一大段业务逻辑，建议要求抽到 src/server/services/* 或按已有 registerXRoutes(app, deps) 模式拆。

6. 前端扫盲

如果你不太懂前端，先把 React 的几个概念建立起来。这个项目用的是 React + TypeScript + Vite。

组件是什么

组件就是一个函数，返回一段 UI。比如 WorkspaceShell 返回整个工作台布局。 组件会根据 props、state、context 重新渲染。

state 是什么

useState 保存组件内部状态。状态变了，React 会重新跑组件函数并更新 DOM。 review 时要看状态是否属于这个组件，还是应该上移到 domain hook/context。

effect 是什么

useEffect 用来做副作用，比如加载数据、注册事件、启动定时器。 review 时重点看依赖数组是否正确、是否清理监听器/定时器。

context 是什么

WorkspaceContext 像一个全局工作台状态包。所有 view 通过 useWorkspace() 读写共享状态。好处是清楚，坏处是过宽会让耦合和重渲染增加。

React review 常见问题

问题 怎么识别 应该怎么做
effect 依赖错 useEffect(..., []) 里读了会变化的变量。 补依赖，或用 ref/trampoline 说明为什么稳定。
状态放错地方 兄弟组件互相传很多 props，或组件直接操作 sibling。 放进 context/domain hook/registry command。
异步竞态 用户切换 source 后，旧请求回来覆盖新 source 状态。 用 cancelled flag、request id，或按 sourceId 检查。
重复提交 Save 按钮连点会创建两条 note。 先清 pending state，再发异步；或禁用按钮。
UI 状态不可恢复 布局/打开状态只存在组件 state，刷新丢失。 明确哪些是 ephemeral，哪些应该持久化到 note/display/prefs。

前端文件后缀

  • .ts：纯 TypeScript，没有 JSX UI。
  • .tsx：React 组件，里面可以写 JSX。
  • .css：样式。
  • .test.ts(x)：Vitest 单测。
  • .spec.ts：通常是 Playwright e2e。

7. 前端架构

整体结构

src/client/main.tsx -> inject themes, detect platform -> App -> PlatformProvider -> LocaleProvider -> FocusProvider -> WorkspaceProvider -> WorkspaceShell(layout preset) -> dock tree -> renderNode(node, ctx) -> registered view component

WorkspaceShell 和 ViewRegistry

工作台不是固定写死三栏。presets.ts 定义 layout tree， WorkspaceShell 遍历 tree，遇到 leaf 就按 node.kind 去 viewRegistry 找 view。 

registerView({
  kind: "review.panel",
  render: (node, ctx) => <ReviewPanel ctx={ctx} />
});

这意味着新增一个面板时，正常路径应该是注册 view，然后把 node 加到 preset 或导航入口。 不应该直接去 App.tsx 或 WorkspaceShell.tsx 硬插 JSX。

WorkspaceContext 和 domain hooks

WorkspaceContext.tsx 曾经是一个大对象，现在已经拆成多个 domain hook：

  • useDocumentsDomain.ts：source、open panes、reader bundle、anchors、notes、layers。
  • useGenerationDomain.ts：AI draft preview、regenerate、auto-materialize。
  • useComposerDomain.ts：右侧输入框、图片附件、提交。
  • useAgentDomain.ts：agent 工具调用、chat context、provider 能力。
  • useOperationDomain.ts：自定义 AI action、toolbar action 顺序。
  • usePluginDomain.ts：插件偏好、贡献开关。
  • useConceptDomain.ts：概念标注反馈、undo。
  • useLayoutDomain.ts / useThemeDomain.ts：布局和主题。
review 提醒：domain hook 拆出来不代表没有耦合。看新增字段是否真的属于该 domain； 不要把所有新状态又塞回 WorkspaceContextValue，除非多个 view 确实需要。

Reader / Viewer

Source 类型通过 src/client/viewers.ts 映射到 viewer：

sourceType viewer kind 典型组件
html, markdown html LocalHtmlReader, DOM reader pipeline
webpage web snapshot + live web tabs
web_live webview Electron/webview guest preload
pdf pdfjs PdfReader
image image ImageReader

CommandRegistry

用户动作不是散落在按钮里直接写逻辑，而是注册为 command。 按钮、快捷命令、toolbar、AI action 都可以 dispatch 同一个 command。

button click -> ctx.dispatch("anchor.add-note", payload) -> runCommand(commandId, commandContext) -> command uses entityClient / focus / actions -> actions callback updates UI state

评审 command 时重点看：

  • isAvailable() 是否正确禁用无效状态。
  • 是否只通过 CommandContext 访问外部世界。
  • 是否重复 materialize anchor。
  • 异步后是否调用 onNoteCreated、onLayersChanged 等刷新回调。

8. AI 链路

AI 层分两部分：底层 provider 只负责模型能力；上层 command/operation/kit 负责业务 prompt。 重要原则是 src/ai 不应该 import kit。

Provider 能力

能力 含义 review 点
chat 能普通对话。 chat route 是否 fallback 正确。
streaming 能增量输出。 没有 stream 的 provider 是否单 chunk fallback。
structured 能原生 JSON 输出。 否则走 extractJson + retry，必须 schema parse。
tools 能跑 app-defined tools。 agent 按钮必须 capability gated。
vision 能看图片。 服务端必须在调用前 gate，不支持时返回干净 400。
kind mock / cli-agent / http / managed。 managed 默认不能带出 learner profile。

普通聊天链路

UI composer -> dispatch("anchor.ask-ai") -> command builds ChatRequest + ChatContext -> entityClient.chatStream() or chat() -> POST /api/chat/stream or /api/chat -> src/server/services/ai.ts -> provider.stream() or complete() -> UI appends assistant chunks/message

结构化生成链路

toolbar action / kit command / operation.run -> entityClient.generateStructured() -> POST /api/kits/generate -> generateKitContent() -> composeAutoContext() -> generateOperationContent() -> src/ai/structured.ts generateStructured() -> zod schema parse -> pending draft preview -> user Save -> create note

AI review 必查

  • AI 返回内容是否必须经过 zod schema 校验再保存。
  • 图片是否只传 assetId 到后端，后端按 provider vision 能力解析 bytes。
  • managed provider 是否剥离 profileContext。
  • CLI provider 是否 strip 可能导致计费的 API key。
  • mock provider 是否保持 deterministic，测试不应依赖真实模型。
  • 生成结果是否先进入 preview，除非明确是 auto-materialize draft 流程。

9. Kit / Plugin

Kit 是一组学习场景能力，Plugin 是更小的贡献单位。当前代码里很多 kit 是 register-only： 它们注册 command、view、note type、prompt，但不一定出现在市场里。

服务端 kit 注册

installServerKits() 在 createApp() 时运行，注册 React-free 的内容： NoteContentSpec、prompt、layer policy、subject detection。

客户端 kit 注册

src/kits/clientKits.tsx 导入产品 kit，并调用 installClientKits(productKits)。 客户端注册 React renderer、command、view 等。

review kit/plugin 时问这些问题

  • 这个能力应该是 core 还是普通 kit？垂直场景通常不该进 core。
  • 新增 note type 是否同时有服务端 content spec 和客户端 renderer。
  • contentType id 是否稳定；如果改名，是否提供 alias。
  • 插件启用/禁用是否通过 contribution prefs，而不是到处 if kitId。
  • 市场安装状态是否只影响“可创建/可见入口”，不应让旧 note 无法渲染。

10. Electron

Electron 有两个世界：main process 有 Node 权限，renderer 是网页。安全 review 的核心是： renderer 不直接拿 Node；需要本地能力时走 preload 暴露的窄 IPC。

文件 作用 review 点
electron/main.ts 窗口、server、dialog、shell、updater。 nodeIntegration:false、contextIsolation:true 是否保持。
electron/preload.ts 暴露 window.studyVault。 暴露 API 是否窄、参数是否校验。
electron/webview-preload.ts webview guest 内选择文本和注入标记。 不要扩大到任意页面脚本能力。
electron/pty-bridge.ts 终端/PTY 桥。 进程生命周期、测试 fake spawner、API key strip。

11. 按改动类型 review

新增 Note 类型

  1. 服务端：是否注册 NoteContentSpec，包含 zod schema、default、toSearchText。
  2. 客户端：是否注册 renderer/editor，不改核心 Note schema。
  3. 搜索：toSearchText 是否提取真正可搜索文本。
  4. 旧数据：contentType 改名是否有 alias。
  5. UI：是否复用统一 note card 外壳。
  6. 测试：schema parse、render、create/update API。

新增 Source / Viewer

  1. sourceTypeSchema 是否新增类型。
  2. ingest/import 是否生成 source record 和原始内容。
  3. src/client/viewers.ts 是否注册 viewer。
  4. reader 是否能产出 Anchor draft。
  5. 已有 anchors 是否能 paint 回原文。
  6. 跳转 anchor 是否能定位。

改 Anchor / Note 可见性

  1. 确认 anchor painting 是从 note + layer 推导，而不是直接 paint 全部 anchors。
  2. 删除 note 时是否处理 orphan anchors。
  3. 多 layer membership 是否用 OR 逻辑。
  4. sealed/imported content 是否只读。
  5. PDF/image/html/web 四类 reader 是否都覆盖。

新增 AI action / operation

  1. prompt 是否在 kit prompt registry 或 operation store 里，而不是写死 UI。
  2. 输入变量是否来自 anchorText、sourceTitle、existingNotes 等声明来源。
  3. 输出 contentType 是否固定或走 form router。
  4. 输出是否 zod 校验。
  5. 是否进入 preview/save 流程。
  6. managed provider 的隐私 gate 是否覆盖。

改工作台 UI

  1. 新增面板是否走 registerView。
  2. 新增按钮是否走 command 或已有 domain action。
  3. 是否支持 loading/error/empty 状态。
  4. 是否避免把业务逻辑塞进 JSX。
  5. 是否有 title/aria-label，尤其是 icon button。
  6. 是否对移动/窄屏有基本约束。

改后端 route

  1. route 是否只做 parse、调用 service、返回 response。
  2. service 是否可被 directTransport 或测试复用。
  3. 是否使用 typed error。
  4. 是否有权限/只读保护，例如 sealed notes。
  5. 是否有输入大小限制，特别是图片/音频/base64。

13. 测试怎么选

不要每次都盲跑最重的测试。先按改动范围选。

改动范围 建议命令 说明
类型、导入、边界、移动端禁用规则 npm run check tsc --noEmit + mobile import guard。
纯函数、service、schema、store、domain hook npm test -- path-or-pattern
npm test		 优先跑聚焦测试，再决定是否全量 Vitest。
reader、selection、anchor painting、普通 UI 流程 npm run e2e Playwright web e2e，使用临时 vault 和 mock AI。
Electron、preload、webview、pty、窗口能力 npm run e2e:electron 会先 build Electron main/preload/client。
打包或生产启动 npm run electron:build
npm run dist:dir		 关注 native deps、external、asarUnpack、userData vault。

测试失败时怎么判断

  • 先看是不是改动范围内的失败，不要被无关 flaky 带偏。
  • 如果是类型失败，通常是 registry 类型、schema 默认值、capability 字段没有补全。
  • 如果是 e2e 失败，优先看 UI 文案/selector 是否变化、异步等待是否不稳定。
  • 如果 Electron e2e 失败，先区分 renderer 错、preload IPC 错、main process 启动错。

14. 已知风险

风险 现状 review 时怎么防
服务端 app.ts 过大 仍有大量 inline routes。 新增复杂逻辑要求进 service 或 route module。
WorkspaceContext 仍然很宽 已拆 domain hooks，但最终 context value 仍大。 新增字段先问是否只属于一个 view/domain。
Reader 层未完全统一 PDF/Image/HTML/Web 有各自 selection/paint 逻辑。 改 anchor painting 必须跨 reader 检查。
文档漂移 部分设计文档里的行数、默认引擎说明可能旧。 以当前代码为准，必要时要求更新文档。
AI provider 能力复杂 mock、CLI、HTTP BYOK、managed 行为不同。 capability gate 和隐私 gate 必须服务端兜底。
Electron 权限边界 需要本地文件、webview、pty 等强能力。 任何新 IPC 都要窄接口、参数校验、不可暴露任意 shell。

路径 为什么重要

electron/main.ts 桌面权限、窗口、server 启动、IPC。

按目录理解

  • src/core：纯领域模型、schema、store、算法。尽量不要依赖 React、window、Electron。
  • src/server：Express routes、services、本地文件、data trust、trash、memory。
  • src/client：React UI、workspace、reader、commands、platform adapter。
  • src/ai：模型 provider、结构化生成、agent tools 机制。
  • src/kits：教材、复习、错题、报告等上层组合能力。
  • electron：桌面壳、preload、webview preload、pty bridge。
  • e2e / e2e-electron：端到端测试。

16. 术语表

术语 解释
Vault 本地资料库，包含 .study 元数据、source 文件、assets、exports。
Envelope 每条记录都有的公共字段：id、type、schemaVersion、createdAt、updatedAt、deletedAt 等。
ContentType Note 内容类型，例如 markdown、quiz、flashcard、mistake。每个类型有自己的 schema 和 renderer。
Anchor draft 用户刚选中原文但还没保存成正式 anchor 的临时选择。
PaintAnchor 前端 reader 用来绘制高亮/图标的统一 anchor 表示。
Sealed content 受保护导入的 svpack 内容，通常只读。
Operation 用户可自定义的 AI action，prompt 和变量作为数据存储。
Provider AI 模型接入，例如 mock、Claude/Codex CLI、DeepSeek、managed gateway。
DirectTransport 不用 HTTP、直接调用 service 的传输 seam，面向移动/嵌入场景。
最终判断标准：一个好 PR 应该让新功能接入已有对象和扩展点； 数据能迁移，UI 能解释失败，AI 输出可验证，本地优先和隐私边界不被破坏。
